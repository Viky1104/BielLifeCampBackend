## 2. 先区分三种“编码”

### 2.1 HTTP 状态码

表示请求在 HTTP 层的结果，例如 `401`、`409`、`503`。调用方应先看它，再看响应体中的业务码。

### 2.2 统一响应 `code`

MVC 业务服务和项目自定义 Gateway 过滤器使用以下外层结构：

```json
{
  "code": "0",
  "errorMsg": "",
  "data": {}
}
```

- 成功固定为字符串 `"0"`，`errorMsg` 固定为空字符串，`data` 允许为 `null`。
- 失败使用稳定业务码，`data` 固定为 `null`。
- 成功不一定是 HTTP 200；提交 EHR 同步成功受理时是 HTTP 202，但 `code` 仍为 `"0"`。
- HTTP 200 也不等于后台任务最终成功；EHR 必须继续检查 `data.status`、`data.failureCode` 和 `data.issueCount`。

失败示例：

```json
{
  "code": "AUTH_TOKEN_INVALID",
  "errorMsg": "Request authentication failed",
  "data": null
}
```

### 2.3 EHR 运行码

EHR 是异步任务，存在两套任务结果字段：

- `data.failureCode`：整次运行失败的原因；接口本身通常仍以 HTTP 200、`code="0"` 返回查询结果。
- `data.items[].issueCode`：单个人员问题；运行通常为 `PARTIAL_SUCCEEDED`，不是接口调用失败。

## 3. 故障发生在哪一层

请求按以下顺序处理，先返回错误的层会终止后续处理：

```text
客户端
  -> Gateway 文档访问控制（仅 /doc.html、/openapi/** 等）
  -> Gateway 外部 JWT 与实时会话校验
  -> Gateway 路由、Nacos/LoadBalancer、下游网络
  -> 业务服务内部身份 JWS 与 Redis 授权快照校验
  -> Controller 参数校验与业务逻辑
  -> 全局异常处理
```

快速判断规则：

| 现象 | 优先定位层 |
|---|---|
| `AUTH_TOKEN_*`、`AUTH_ACCOUNT_FORBIDDEN`、`AUTHZ_STALE` | Gateway 认证过滤器 |
| `AUTH_INTERNAL_IDENTITY_*`、`AUTH_LOGIN_CONTEXT_*` | 业务服务安全上下文过滤器 |
| `COMMON_VALIDATION_FAILED`、`PROFILE_*` | system-service Controller/业务逻辑 |
| `EHR_*` 出现在 `failureCode` 或 `issueCode` | EHR 异步运行、EHR 接口或本地持久化 |
| 只有 HTTP 502/503/504，没有 `code/errorMsg/data` | Gateway/框架生成的基础设施错误 |
| `COMMON_INTERNAL_ERROR` | 业务服务未被专用异常处理器接住的异常 |

## 4. 标准排障步骤

1. 记录发生时间、环境、HTTP 方法、完整路径、HTTP 状态、响应 `code`、`X-Request-Id`；EHR 还要记录 `runId`。
2. 确认响应体是否为统一结构。没有统一结构时，先排 Gateway 路由、实例发现、连接和超时。
3. 按本手册的编码表确定故障层，不要只根据 `errorMsg` 判断；Gateway 会有意把下游细节收敛成通用摘要。
4. 用 `request_id`、时间窗口、服务名和错误码查日志。EHR 优先使用 `runId` 和 `failureCode`。
5. 检查 `/actuator/health/readiness`、Nacos 实例、目标服务 Pod/进程、Redis、MySQL及对应外部依赖。
6. 只有确认操作幂等后才能重试。EHR 重试必须复用原 `Idempotency-Key`；令牌刷新失败不能盲目重复提交旧刷新令牌。

建议客户端主动传入请求标识：

```bash
curl.exe -i -H "X-Request-Id: ops-20260806-001" https://<gateway-host>/<path>
```

## 5. HTTP 状态速查

| HTTP | 当前语义 | 是否直接重试 |
|---:|---|---|
| 200 | 同步接口成功，或查询成功 | 不需要；继续检查业务数据 |
| 202 | EHR 同步已受理为 `PENDING` | 不重复提交；按 `runId` 查询 |
| 400 | JSON、字段、路径、查询参数或请求头校验失败 | 修正请求后再提交 |
| 401 | 缺少/无效凭据、会话失效、内部身份失败 | 刷新或重新登录，不原样重试 |
| 403 | 身份存在但员工状态、客户端类型或权限不允许 | 修复状态/授权后再试 |
| 404 | 资源、路由或在线文档不存在/关闭 | 核对路径、配置和资源标识 |
| 409 | 权限版本、绑定、人员匹配或任务状态冲突 | 先解决冲突；不要并发重试 |
| 413 | 上传头像超过 2 MiB | 压缩或更换文件 |
| 422 | 资料字段或头像内容不符合业务语义 | 修正内容后再提交 |
| 500 | 未分类的服务端异常 | 查服务端异常堆栈和数据库/依赖 |
| 503 | 服务实例、配置、缓存、外部平台、存储或队列不可用 | 先确认依赖恢复；幂等请求才可退避重试 |
| 504 | Gateway 等待下游响应超时 | 查下游耗时、线程池、数据库和网络 |

## 6. 公共与 Gateway 编码

### 6.1 公共编码

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `0` | 200/202 | 请求成功；EHR 可能仅表示已受理或查询成功 | 检查 `data`，EHR 再看 `status/failureCode/issueCount` |
| `COMMON_VALIDATION_FAILED` | 400 | 请求体缺失或 JSON 无法解析；字段为空、长度/正则不符；路径/查询参数类型错误；`pageSize`、`afterId`、`Idempotency-Key` 越界 | 对照 OpenAPI 和请求 DTO；检查 Content-Type、字段名和参数类型 |
| `COMMON_RESOURCE_NOT_FOUND` | 404 | URL 无对应 MVC 资源；EHR `runId` 不存在；在线文档开关关闭 | 核对 URL、运行主键和 `KNIFE4J_ENABLED` |
| `COMMON_ROUTE_NOT_FOUND` | 404 | 受保护 `/api/**` 不属于九个固定业务前缀 | 核对 Gateway 路径前缀和路由清单 |
| `COMMON_INTERNAL_ERROR` | 500 | 未处理的运行时异常、数据库异常、序列化异常或代码缺陷 | 用 `request_id` 搜索 `Unhandled request failure` 及其堆栈 |

`COMMON_VALIDATION_FAILED` 当前不会返回具体字段名。常见约束包括：

- 管理员登录：工号必填且最长 64，密码必填且最长 128。
- 微信登录：`loginCode` 必填且最长 512；非空 `phoneCode` 长度 16～512。
- 刷新令牌：必填，长度 32～1024。
- EHR 提交：`Idempotency-Key` 长度 16～128；`runType` 只能为 `FULL_RECONCILIATION`；原因长度 5～500；确认票据长度 16～512。
- EHR 查询：`pageSize` 为 1～100，`afterId` 不小于 0，`syncRunId` 必须能解析为 `long`。

### 6.2 在线接口文档编码

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `AUTH_BASIC_INVALID` | 401 | Knife4j Basic Auth 未提供或用户名/密码错误 | `KNIFE4J_BASIC_ENABLED`、Secret 注入值、Authorization 头 |
| `API_DOCS_CONFIGURATION_INVALID` | 503 | Basic Auth 已开启，但用户名为空/含冒号，或密码少于 12 字符 | Gateway 的 Knife4j 配置和 Secret；修改后按部署方式刷新/重启 |
| `COMMON_RESOURCE_NOT_FOUND` | 404 | `platform.api-docs.enabled=false` | `KNIFE4J_ENABLED` 或 Nacos `gateway.yaml` |

### 6.3 Gateway 外部认证编码

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `AUTH_TOKEN_MISSING` | 401 | 受保护 `/api/**` 没有 `Authorization: Bearer ...`，或头格式不正确 | 客户端请求头；登录/刷新白名单路径是否准确 |
| `AUTH_TOKEN_INVALID` | 401 | JWT 格式、签名、issuer、audience、有效期无效；缺 `sid/authz_ver`；subject 不是员工数字主键 | Gateway 外部公钥、系统时钟、JWT claims、issuer/audience 配置 |
| `AUTH_SESSION_REVOKED` | 401 | system-service 返回 401：会话不存在、已撤销、绝对/空闲过期，或关联员工不存在 | `sys_user_session`、员工记录、Redis 会话；客户端重新登录 |
| `AUTH_ACCOUNT_FORBIDDEN` | 403 | system-service 返回任意 403，通常为员工已离职、账号冻结或目标服务不允许 | `sys_employee.employment_status/account_status`；目标服务映射 |
| `AUTHZ_STALE` | 409 | JWT 中 `authz_ver` 与员工当前权限版本不一致 | 刷新令牌获得新访问令牌；检查权限变更是否符合预期 |
| `AUTH_AUTHORIZATION_UNAVAILABLE` | 503 | Gateway 调实时会话接口超时（3 秒）、网络/解析失败；system-service 返回非 401/403/409；响应 `code` 非 0 或 `data` 为空；Redis/MySQL 认证依赖异常 | system-service readiness、`SYSTEM_AUTHORIZATION_URI`、服务凭据、Redis/MySQL、Gateway 到服务网络 |

注意：Gateway 会收敛 system-service 的返回细节。外部请求看到 `AUTH_ACCOUNT_FORBIDDEN` 时，下游原始原因可能是 `AUTH_EMPLOYEE_RESIGNED` 或 `AUTH_ACCOUNT_FROZEN`；看到 `AUTH_AUTHORIZATION_UNAVAILABLE` 时也可能是下游缓存/数据库故障。

### 6.4 Gateway/框架基础设施状态

当前没有自定义 Gateway 全局异常处理器，因此部分基础设施错误不保证使用统一响应体：

| 现象 | 可能原因 | 首查项 |
|---|---|---|
| HTTP 404 且无业务码 | Nacos 配置中没有该路由、路由谓词不匹配、Gateway 仍是旧配置 | Nacos `gateway.yaml` 完整 routes 列表、配置刷新和 Gateway 版本 |
| HTTP 503 且无业务码 | Nacos 中目标服务无可用实例、LoadBalancer 无实例、连接失败 | 服务注册 Namespace/Group/Cluster、实例健康、端口和 NetworkPolicy |
| HTTP 504 且无业务码 | 下游超过 Gateway 默认 30 秒响应超时 | 下游线程/连接池、慢 SQL、外部依赖、`GATEWAY_RESPONSE_TIMEOUT` |
| HTTP 403 且无业务码 | CORS 来源、方法或请求头不在允许列表 | Gateway `globalcors` 配置和实际 Origin/预检请求 |

## 7. 内部身份与授权上下文编码

这些编码由各 MVC 业务服务的 `starter-security-context` 或 system-service 内部接口返回。

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `AUTH_INTERNAL_IDENTITY_MISSING` | 401 | Controller 需要可信身份，但请求绕过 Gateway，或 Gateway 未注入 `X-Internal-Identity` | 是否从 Gateway 访问；Gateway 认证是否开启；过滤链是否执行 |
| `AUTH_INTERNAL_IDENTITY_DISABLED` | 401 | 请求带内部 JWS，但目标服务未启用内部身份验证或 JwtDecoder 未装配 | `INTERNAL_IDENTITY_ENABLED`、公钥和服务启动配置 |
| `AUTH_INTERNAL_IDENTITY_INVALID` | 401 | 内部 JWS 签名、issuer、audience、有效期或必需 claims 无效 | Gateway 内部私钥与服务公钥是否配对；目标服务 audience；时钟偏差 |
| `AUTH_LOGIN_CONTEXT_UNAVAILABLE` | 503 | 授权缓存启用但 Store 未装配，或 Redis 访问异常 | `AUTHORIZATION_CACHE_ENABLED`、Redis 连接、前缀和 TTL 配置 |
| `AUTH_LOGIN_CONTEXT_MISSING` | 503 | Redis 中找不到员工 + 目标服务 + 权限版本对应的授权快照 | system-service 是否写入缓存；TTL/淘汰；版本和服务名是否一致 |
| `AUTH_LOGIN_CONTEXT_INVALID` | 401 | Redis 快照与内部 JWS 的员工、会话、目标服务或权限版本不一致 | 清理异常快照并由权威流程重建；核对发布期间版本兼容性 |
| `AUTH_SERVICE_IDENTITY_INVALID` | 401 | 直接调用内部会话接口时 `X-Gateway-Service-Token` 缺失或错误 | Gateway 与 system-service 的 `AUTH_GATEWAY_SERVICE_TOKEN` 是否一致且至少 32 字符 |
| `AUTH_TARGET_SERVICE_INVALID` | 403 | 内部会话请求中的目标服务不在九个固定服务名单 | Gateway 的路径到服务映射；禁止客户端直调内部接口 |

## 8. system-service 认证与会话编码

### 8.1 功能、配置和依赖

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `AUTH_DISABLED` | 503 | `platform.auth.enabled=false`，或令牌签发器因认证关闭未装配 | system-service 认证开关和启动配置 |
| `AUTH_EHR_INITIAL_SYNC_REQUIRED` | 503 | 配置要求首次 EHR 同步，但 `sys_integration_state.initial_sync_completed` 仍为 false/缺失 | 最近 EHR 运行状态和集成状态；不得手工绕过数据门禁 |
| `AUTH_ADMIN_PASSWORD_DISABLED` | 503 | 本地管理员密码登录开关关闭 | `platform.auth.admin-password.enabled`；确认是否应该开放 |
| `AUTH_LOGIN_RATE_LIMIT_UNAVAILABLE` | 503 | Redis 访问失败、计数值损坏、删除/递增失败 | Redis readiness、限流键 TTL、连接和权限 |
| `AUTH_AUTHORIZATION_UNAVAILABLE` | 503 | Redis 会话或授权缓存访问异常 | Redis、缓存开关、key 前缀和 system-service 日志 |

### 8.2 微信登录和员工绑定

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `AUTH_WECHAT_NOT_CONFIGURED` | 503 | AppId 或 AppSecret 为空 | Secret 注入和 WeChat 配置，禁止在日志/Nacos 写明文密钥 |
| `AUTH_WECHAT_UNAVAILABLE` | 503 | 微信 HTTP 非 2xx、连接/读取超时、DNS/网络失败、JSON 序列化异常 | 外网连通、微信接口状态、5 秒连接/8 秒请求超时、代理和 DNS |
| `AUTH_WECHAT_RESPONSE_INVALID` | 503 | `jscode2session` 成功响应缺少 `openid` | 脱敏检查微信响应契约和 App 配置 |
| `AUTH_WECHAT_PHONE_RESPONSE_INVALID` | 503 | 手机号接口成功响应缺 `phone_info.purePhoneNumber` | 手机号授权流程、微信响应契约 |
| `AUTH_WECHAT_TOKEN_RESPONSE_INVALID` | 503 | 稳定 access token 响应缺 `access_token` | App 凭据、微信 token 响应和时钟 |
| `AUTH_WECHAT_CODE_INVALID` | 401 | 微信响应 `errcode != 0`，登录码/手机号码无效、过期、已使用，或平台拒绝请求 | 让客户端重新获取一次性 code；核对 AppId/环境 |
| `AUTH_WECHAT_PHONE_REQUIRED` | 403 | 首次微信绑定没有提供 `phoneCode` | 已绑定用户不需要；首次绑定重新授权手机号 |
| `AUTH_WECHAT_PHONE_INVALID` | 403 | 微信返回的手机号无法通过系统规范化 | 检查国家区号/号码格式和上游数据，不记录完整手机号 |
| `AUTH_EHR_EMPLOYEE_NOT_FOUND` | 403 | 经摘要匹配后，没有在职 EHR 员工使用该手机号 | 最近 EHR 同步、员工在职状态、手机号数据质量 |
| `AUTH_EHR_EMPLOYEE_AMBIGUOUS` | 409 | 同一手机号匹配多个在职员工，系统拒绝自动绑定 | EHR 重复手机号治理，人工确认身份，禁止强行选第一条 |
| `AUTH_WECHAT_BINDING_CONFLICT` | 409 | 并发绑定或唯一约束冲突，OpenID/员工已有不兼容绑定 | `sys_external_identity` 唯一关系、并发请求和历史绑定状态 |

### 8.3 管理员登录、刷新和员工状态

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `AUTH_INVALID_CREDENTIALS` | 401 | 工号不存在或密码错误；两者有意返回同一码防账号枚举 | 由授权管理员核对账号和凭据；查看审计 `detail_code` |
| `AUTH_LOGIN_RATE_LIMITED` | 401 | 账号或来源 IP 在限流窗口达到失败阈值 | 等待窗口过期；检查是否遭遇暴力尝试；不要关闭保护绕过 |
| `AUTH_REFRESH_INVALID` | 401 | 刷新令牌摘要不存在，可能为伪造、过期清理或错误环境令牌 | 客户端重新登录；不要在服务端查询/记录原始令牌 |
| `AUTH_REFRESH_REPLAYED` | 401 | 已消费/已撤销的刷新令牌再次使用；代码会撤销整个令牌族和会话 | 排查并发刷新、客户端重复提交或令牌泄露；重新登录 |
| `AUTH_SESSION_REVOKED` | 401 | 会话缺失、状态非 ACTIVE、绝对/空闲过期；刷新令牌过期；用户已退出 | 查 `sys_user_session` 和刷新令牌状态；重新登录 |
| `AUTH_EMPLOYEE_NOT_FOUND` | 401 | 会话/缓存引用的员工主键已不存在 | 检查员工投影完整性和异常数据删除 |
| `AUTH_EMPLOYEE_RESIGNED` | 403 | `employment_status != ACTIVE` | 核对 EHR 最近同步和离职状态 |
| `AUTH_ACCOUNT_FROZEN` | 403 | `account_status != ACTIVE` | 核对冻结原因和管理员操作，解冻需走授权流程 |
| `AUTHZ_STALE` | 409 | 员工当前 `authz_version` 与访问令牌版本不同 | 使用有效刷新令牌轮换；确认 RBAC 变更 |
| `AUTH_ADMIN_ACCESS_DENIED` | 403 | EHR 管理接口不是 `ADMIN_WEB` 会话，或缺 `system:ehr-sync:read/execute` 权限 | 会话客户端类型、角色分配和权限码 |

## 9. 用户资料编码

| 编码 | HTTP | 可能原因 | 首查项 |
|---|---:|---|---|
| `PROFILE_NICKNAME_INVALID` | 422 | JSON 缺 `nickname` 成员；非 null 昵称去空白后为空、超过 32 个 Unicode 字符或含控制字符 | 请求 JSON 是否显式包含成员；前后端长度计算和不可见字符 |
| `PROFILE_IDENTITY_MISSING` | 409 | 写资料时找不到当前员工的有效微信身份，或并发插入后仍无法更新资料记录 | 当前微信绑定、`sys_external_identity` 状态和并发请求 |
| `PROFILE_AVATAR_TOO_LARGE` | 413 | Multipart 声明或实际读取超过 2 MiB | 文件大小、反向代理/Gateway 限制；客户端压缩 |
| `PROFILE_AVATAR_INVALID` | 422 | `avatar` part 缺失/为空；不是可解码 JPEG/PNG/WebP；宽高超过 8192；总像素超过 16,777,216；文件读取失败 | Multipart 名必须为 `avatar`；验证真实文件内容而非扩展名 |
| `PROFILE_STORAGE_UNAVAILABLE` | 503 | OSS 功能关闭；上传或签名 URL 失败；Bucket、Endpoint、凭据、权限或网络异常 | `platform.profile.storage` 配置、Workload Identity/凭据、Bucket ACL/权限和 OSS 网络 |

已知降级语义：查询 `/api/system/v1/me` 时，如果已有头像对象但签名 URL 失败，接口仍返回 `code="0"`，同时 `avatarUrl=null`，日志包含 `Profile avatar signing unavailable`。头像替换后的旧对象删除失败也不回滚成功响应，日志包含 `Profile avatar cleanup failed`。

## 10. EHR 同步运行与问题编码

### 10.1 正确读取 EHR 返回

人工提交成功时：

```text
HTTP 202 + code="0" + data.status="PENDING"
```

随后使用 `runId` 查询，最终状态为：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `PENDING` | 已落库，等待本实例后台线程 | 短间隔轮询；长期不变时查执行器和实例重启 |
| `RUNNING` | 已取得集群租约并执行 | 结合阶段日志观察进度 |
| `SUCCEEDED` | 全量同步完成且无人员问题 | 完成 |
| `PARTIAL_SUCCEEDED` | 主流程完成但 `issueCount > 0` | 查询 issues；当前批次会跳过缺失人员离职对账 |
| `FAILED` | 整次运行失败 | 查 `failureCode`、`failureDigest` 和相同 `runId` 日志 |

### 10.2 EHR 运行 `failureCode`

| 编码 | 出现位置 | 可能原因 | 首查项 |
|---|---|---|---|
| `EHR_SYNC_QUEUE_FULL` | HTTP 503，同时运行记为 FAILED | 当前实例 EHR 提交执行器队列已满或正在关闭 | 活跃/积压任务、实例是否优雅停机；复用原幂等键查询已有运行 |
| `EHR_SYNC_ALREADY_RUNNING` | 通常为异步运行 `failureCode`；同步异常映射为 HTTP 409 | `sys_task_lease` 中已有未过期的同类 RUNNING 租约 | 当前租约、已有 runId、租约到期时间；不要并发再触发 |
| `EHR_INVALID_PAGE_COUNT` | 运行 `failureCode` | EHR 返回总页数小于 1 或超过 `EHR_MAX_PAGES` | 第一页元数据和分页配置 |
| `EHR_RECORD_LIMIT_EXCEEDED` | 运行 `failureCode` | EHR 声明总人数超过 `EHR_MAX_RECORDS` 内存安全阈值 | 确认真实人员规模；评估资源后再调整阈值 |
| `EHR_RESPONSE_INVALID` | 运行 `failureCode` | JSON 无法解析；`data.data` 不是数组；总数/页数缺失或为负；总人数超过页数×页大小；其他契约结构异常 | EHR/ESB 契约版本、脱敏后的响应结构、分页元数据 |
| `EHR_RESPONSE_REJECTED` | 运行 `failureCode` | EHR 响应外层 `code` 不是 `0` | ESB 鉴权头、路由、服务名、上游业务错误；禁止记录原始敏感响应 |
| `EHR_PAGE_FETCH_INTERRUPTED` | 运行 `failureCode` | 等待并发分页时线程被中断，常见于实例停机或任务取消 | Pod/进程重启、线程中断、部署时间线 |
| `EHR_PAGE_FETCH_FAILED` | 运行 `failureCode` | 分页 Future 以非运行时异常失败 | 同一 runId/pageNo 的异常链和线程池状态 |
| `EHR_PAGING_CHANGED` | 运行 `failureCode` | 后续页返回的总页数/总人数与第一页不一致 | EHR 分页快照一致性；上游是否边查边变更统计 |
| `EHR_PAGE_SIZE_EXCEEDED` | 运行 `failureCode` | 单页返回记录数超过请求的 `pageSize` | ESB/EHR 是否忽略分页参数 |
| `EHR_EMPTY_SNAPSHOT` | 运行 `failureCode` | 全量在职人员快照总数为 0 或列表为空 | 上游过滤条件、EHR 可用性；这是安全门禁，不能继续离职对账 |
| `EHR_SNAPSHOT_COUNT_MISMATCH` | 运行 `failureCode` | 汇总后的实际人员数与声明总人数不一致 | 缺页、重复/变化分页、分页返回规模 |
| `EHR_SYNC_TECHNICAL_FAILURE` | 运行 `failureCode` | 未分类运行时异常，例如 EHR HTTP 连接/读取异常、MySQL/事务异常、任务租约或程序缺陷 | 日志中的 `failureStage`、异常类型和完整堆栈；数据库/网络/线程池 |

### 10.3 人员级 `issueCode`

以下编码不会直接作为 HTTP 失败返回。存在任一问题时运行状态为 `PARTIAL_SUCCEEDED`，问题写入 `sys_ehr_sync_issue`：

| 编码 | 阶段 | 可能原因 | 影响 |
|---|---|---|---|
| `EHR_REQUIRED_FIELD_MISSING` | `VALIDATING` | 工号或姓名为空/全空白 | 该人员跳过 |
| `EHR_DUPLICATE_IDENTITY` | `VALIDATING` | 同一快照内工号重复 | 重复人员跳过 |
| `EHR_MOBILE_INVALID` | `VALIDATING` | 非空手机号不能规范化 | 该人员跳过 |
| `EHR_EMPLOYEE_PERSIST_FAILED` | `PERSISTING` | 单人员工投影写入发生数据库/约束/事务异常 | 该人员失败，其他人员继续 |
| `EHR_SUPERVISOR_LINK_FAILED` | `SUPERVISOR_LINKING` | 上级关系更新失败或依赖记录异常 | 该人员上级关系未正确生效 |
| `EHR_DEFAULT_ROLE_INITIALIZATION_FAILED` | `DEFAULT_ROLE_INITIALIZING` | 默认 `EMPLOYEE` 角色分配失败 | 该人员可能缺少基础角色 |

为防止错误离职，存在人员问题时本批次跳过“将快照中缺失员工标记离职”的对账步骤。

## 11. 只读数据库查询

以下 SQL 仅用于 system-service 私有库排障。不要跨服务直接写库，不要查询或输出密码哈希、Token、OpenID、完整手机号等敏感值。

### 11.1 EHR 最近运行

```sql
SELECT id,
       status,
       trigger_type,
       fetched_count,
       inserted_count,
       updated_count,
       resigned_count,
       role_initialized_count,
       issue_count,
       failure_code,
       failure_digest,
       started_at,
       completed_at,
       created_at
FROM sys_ehr_sync_run
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

### 11.2 指定 EHR 运行及人员问题

将示例主键替换为实际 `runId`：

```sql
SELECT id, status, issue_count, failure_code, failure_digest,
       started_at, completed_at, created_at
FROM sys_ehr_sync_run
WHERE id = 1900000000000000001;

SELECT id, severity, issue_code, employee_no,
       failure_stage, detail_digest, created_at
FROM sys_ehr_sync_issue
WHERE run_id = 1900000000000000001
ORDER BY id;
```

### 11.3 EHR 活跃租约

```sql
SELECT task_type,
       task_id,
       idempotency_key,
       attempt,
       lease_expires_at,
       status,
       failure_digest,
       updated_at
FROM sys_task_lease
WHERE task_type = 'EHR_EMPLOYEE_FULL_SYNC';
```

不要因看到旧的 `RUNNING` 状态就直接改表。先比较 `lease_expires_at` 与数据库 UTC 时间、确认实例是否仍在执行，并按任务恢复流程处理。

### 11.4 EHR 首次同步门禁

```sql
SELECT connection_code,
       initial_sync_completed,
       last_successful_watermark,
       last_successful_at,
       updated_at
FROM sys_integration_state
WHERE connection_code = 'EHR';
```

### 11.5 员工与会话状态

仅在获授权的排障环境中，用实际员工 ID 或会话 ID 替换示例：

```sql
SELECT id, employee_no, employment_status, account_status,
       authz_version, binding_status, last_ehr_synced_at, updated_at
FROM sys_employee
WHERE id = 1900000000000000001;

SELECT id, employee_id, client_type, auth_method, status,
       authz_version_at_issue, absolute_expires_at, idle_expires_at,
       last_seen_at, revoked_at, revoke_reason, created_at
FROM sys_user_session
WHERE id = '00000000-0000-0000-0000-000000000000';
```

### 11.6 认证审计

```sql
SELECT occurred_at,
       actor_employee_id,
       action,
       result,
       detail_code,
       request_id
FROM sys_operation_audit
WHERE module = 'AUTH'
ORDER BY occurred_at DESC
LIMIT 100;
```

当前认证审计的 `request_id` 是业务层单独生成的 UUID，并非 HTTP `X-Request-Id`，只能结合发生时间、员工和 `detail_code` 关联，不能直接与访问日志一一匹配。

## 12. 日志查询关键字

| 场景 | 建议关键字 |
|---|---|
| 未处理异常 | `Unhandled request failure`、`requestId=<值>` |
| EHR 整体失败 | `event=ehr_employee_sync_failed`、`runId=<值>`、`failureCode=<值>` |
| EHR 分页失败 | `event=ehr_page_fetch_failed`、`pageNo=`、`requestId=` |
| EHR 队列满 | `event=ehr_employee_sync_submission_rejected` |
| EHR 跳过离职对账 | `event=ehr_reconciliation_skipped`、`reason=PERSONNEL_ISSUES_PRESENT` |
| 头像签名降级 | `Profile avatar signing unavailable`、`employeeId=` |
| 头像清理补偿失败 | `Profile avatar cleanup failed`、`employeeId=` |

日志默认输出 ECS JSON，优先按稳定服务名、`request_id`、时间范围查询。不得在排障记录中粘贴 Token、密码、Cookie、AppSecret、完整手机号、OpenID 或原始 EHR 响应。

## 13. 当前可观测性限制

1. Gateway 认证过滤器和内部身份过滤器返回业务码时通常不记录对应告警日志，需要结合 Gateway 访问日志、响应时间和 system-service 日志判断。
2. `PROFILE_STORAGE_UNAVAILABLE` 会把 OSS 原始异常收敛为安全摘要，当前响应路径没有保留根因日志；只能结合 OSS 指标、配置、云审计和同时间窗口日志排查。
3. Gateway 基础设施异常没有统一错误响应包装，502/503/504 可能只有 Spring WebFlux 默认响应。
4. `COMMON_VALIDATION_FAILED` 不返回具体失败字段，需要对照 OpenAPI 或在安全环境复现。
5. 认证审计 UUID 与 HTTP `X-Request-Id` 尚未贯通。

这些限制不改变错误码语义，但会影响定位速度。后续补充日志或指标时应保持响应码兼容，且不得泄露安全细节。

## 14. 文档维护方法

新增或修改接口异常行为时，至少检查以下来源：

```powershell
rg -n 'ApiResponse\.failure|@ExceptionHandler|AuthException|EhrSyncException|ProfileException' `
  platform-starters gateway services

rg -n '"(COMMON|AUTH|AUTHZ|PROFILE|EHR|API_DOCS)_[A-Z0-9_]+"' `
  platform-starters gateway services
```

第二条会同时命中部分配置常量或任务类型，必须人工确认它是否真的能出现在响应 `code`、EHR `failureCode` 或 `issueCode` 中。同步更新本手册、OpenAPI 错误状态、相关测试和运维查询。
